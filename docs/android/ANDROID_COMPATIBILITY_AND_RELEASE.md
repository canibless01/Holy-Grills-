# Holy Grills Android: compatibility, verification and release

This work is isolated on `android-app`, starting at main commit `7c1a844`. It bundles the existing React 18 / Vite 6 / React Router 6 frontend in Capacitor; it does not load the production website as a remote WebView shell. Existing backend, Supabase project, account identities, payments, order rules and financial data remain authoritative. No database migration is needed.

## Implemented

- Capacitor 8.6.3, Android compile/target SDK 36, minimum SDK 24 (Android 7+), JDK 21 and Gradle 8.14.3. Native OneSignal plugin 1.0.6 is pinned exactly from OneSignal's official stable release feed. FCM's public Android configuration probe returned `fcm_live` for the existing OneSignal app. Google Play Services is needed for FCM delivery; browser push alone is not evidence of Android delivery.
- Android assets reuse the existing Holy Grills mark. Launcher, adaptive icon, splash and monochrome notification icon are generated by `npm run android:assets`.
- WebView runs bundled assets at `https://localhost`, with HTTPS-only API transport and no mixed content. Bearer-token API requests use Capacitor HTTP, avoiding a production CORS change. Browser requests keep ordinary fetch. No backend authentication/checkout/cutoff or payment-confirmation rule was changed.
- Android JWTs are held in memory while in use and persisted with AES-GCM using a non-exportable Android Keystore key. They are not persisted as ordinary WebView localStorage/sessionStorage tokens. Restore completes before account bootstrap. Writes are coalesced and serialized so refresh/login cannot overwrite a later logout. Remember-me off keeps credentials session-only. App backup is disabled. A failed vault load offers Retry or Sign in again. Browser token storage is unchanged.
- Existing accounts work in the app, but browser and Android sessions are separate. Installing the APK does not copy a browser login or create a second account.
- OneSignal initializes once through one native wrapper. Account IDs use the existing profile UUID as External ID. Login/logout/device registration are serialized; logout clears displayed notifications and disassociates identity. Subscription observers and an immediate ID check register genuine Android subscriptions through the existing device endpoint. Explicit enable respects the native permission and updates the existing account preference. Web OneSignal remains in place; web workers are not registered inside the APK. Web IAM campaigns are paused on native until configured/tested separately.
- Notifications request permission from the Allow action. GPS is requested only by Use my location. No contacts, microphone, camera or broad shared-storage permission is added. File selection and document sharing use system pickers. Internet/network/FCM background permissions do not show runtime dialogs. Unknown-source installation approval belongs to the browser/Files app, not a broad installer permission requested by Holy Grills.
- Android back closes supported dialogs, navigates app history, or minimizes at the root. System-bar handling uses Capacitor's native insets support and a contained native viewport. Keyboard uses resize behaviour. PWA installation UI is suppressed inside native.
- Paystack opens in a browser tab. A bounded saved return context restores the existing verification route after browser close/app resume, including guest claim proof. HTTPS App Links also support cold/warm callback and notification opens after domain association is published. No local return flag is trusted as payment success. A cancelled payment remains pending and the existing server/card verification decides the outcome.
- Native GPS, Android sharing and ticket-PDF saving/sharing are connected. Native files use app cache/FileProvider, not a broad storage grant. Customer layouts are retained.
- Update checks use a small public manifest, are delayed and limited to once daily, and never block ordering. Only official Holy Grills or this repository's HTTPS APK release URLs with a valid version/checksum manifest are accepted. Android still performs signing-certificate validation during an update.

## Device-specific website installation

`/android` is the download page. Homepage/install controls use a small local OS hint, including iPad desktop-mode detection: Android gets APK download when a signed release is enabled; iPhone/iPad gets the existing visual Add to Home Screen guide. No permission, server lookup or stored fingerprint is needed for OS detection. APK availability is a tiny asynchronously fetched static manifest, shared/cached by the install UI; iOS does not fetch that manifest for the homepage card. Existing native/standalone sessions suppress installation UI. A browser cannot reliably enumerate arbitrary sideloaded apps, so this is not a claim to detect all installed APKs from an ordinary browser tab.

Safari does not expose a website API that opens its browser toolbar Share menu and finishes Add to Home Screen. The iOS button opens the visual guide; the customer makes those final Safari taps. An iPhone cannot install an APK. Existing iPhone PWA accounts/orders/wallet/rewards remain shared with the platform; installed web push requires iOS 16.4+ and permission. Native iOS would need a separately signed iOS build and Apple's distribution requirements, not this APK.

`public/android-release.json` stays unavailable until the verified signed main workflow publishes its release pointer. The publisher writes this shape:

```json
{
  "available": true,
  "version": "1.0.0",
  "versionCode": 1,
  "url": "https://github.com/canibless01/Holy-Grills-/releases/download/android-v1.0.0/Holy-Grills-v1.0.0.apk",
  "sha256": "REPLACE_WITH_THE_ACTUAL_64_CHARACTER_APK_SHA256"
}
```

APK hosting uses a versioned release URL. Images remain on Cloudinary. The development branch alone does not activate downloads; merging to main starts the signed publication workflow.

## Build and internal installation

From `holy-grills-frontend` with Node 22+, a full JDK 21, Android SDK platform 36, platform-tools and Android build-tools:

```sh
npm ci
npm run typecheck
npm run lint
npm run test:native
npm run build
npm run android:assets
npm run android:debug
```

Point `ANDROID_HOME` or ignored `android/local.properties` to the Android SDK. `android:debug` bundles a development frontend, syncs native plugins and generates `android/app/build/outputs/apk/debug/app-debug.apk`. It uses package `com.holygrills.app.debug` and label **Holy Grills (Test)**. This allows it to coexist with a later production app signed by the permanent release key. Do not distribute this debug build as the customer release.

`.env.android` contains public production origin/API/App-ID configuration. `.env.android.local` is ignored. Set `VITE_GOOGLE_MAPS_API_KEY` there for local testing or `HG_ANDROID_GOOGLE_MAPS_API_KEY` in GitHub Actions. It is a browser Maps JavaScript/Places key, not a new Android Maps SDK integration. Its allowed referrers must include `https://localhost/*`; restrict it to the APIs in use and set quotas/budget alerts. An existing website key's domain restriction can reject the native origin even while web maps work. Do not paste credentials in chat or commit local configuration. Existing public key reuse for this isolated debug build does not establish its native referrer acceptance.

The manual/push Android GitHub Actions workflow produces downloadable build artifacts and checksums. Release signing is a separate guarded workflow choice.

## Permanent signing and customer release

The production package is `com.holygrills.app`. The permanent signing identity must be backed up securely and reused for every future update.

Generate a keystore privately, for example with the JDK's interactive `keytool` (password prompts, no passwords in command history):

```sh
keytool -genkeypair -keystore holy-grills-release.jks -alias holygrills -keyalg RSA -keysize 3072 -validity 10000
```

Local signed builds need `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, and `VITE_GOOGLE_MAPS_API_KEY`. `npm run android:release` checks these before compiling. Credentials and keys are ignored and never bundled. Never use the debug key as the permanent signing key.

GitHub Actions release choice needs repository secrets:

- `HG_ANDROID_KEYSTORE_BASE64`
- `HG_ANDROID_KEYSTORE_PASSWORD`
- `HG_ANDROID_KEY_ALIAS`
- `HG_ANDROID_KEY_PASSWORD`
- `HG_ANDROID_GOOGLE_MAPS_API_KEY`

The workflow decodes signing material only into the runner's temporary directory and does not print it. It uploads the signed APK, SHA256 and certificate-derived `assetlinks.json` as workflow artifacts. Successful push builds on main also publish the signed release and website pointer, as detailed below.

Publish the **release** certificate association at `https://holygrills.online/.well-known/assetlinks.json`, then verify Android App Links with adb. Do not publish the debug signing association as the production identity. Without verified HTTPS association, closing the payment browser tab still resumes existing server verification, but automatic browser → app callback dispatch needs device acceptance. Custom scheme `holygrills://app/orders/...` also supports controlled app-link testing; it is not proof of domain association.

Bump Android versionCode and versionName for each update, build with the same release key, publish the versioned APK/checksum, then update the public manifest. Keep old APKs versioned; no silent live-update service is introduced.

## Acceptance evidence and outstanding physical checks

Automated adapter tests cover local OS detection, release URL/checksum validation, vault bootstrap, plaintext JWT exclusion, token rotation/logout/remember-me, trusted cold/warm paths, guest claim queries, payment return separation, HTTPS/bearer transport, account-switch races and duplicate device writes. Existing web push tests, the web build/typecheck/lint and actual Android compilation are separately checked. OneSignal’s structural self-check passes all 10 checks against a source-only snapshot; generated bundles are excluded because the upstream SDK itself contains legacy API names. Setup checkpoints remain local.

Device/provider tests must be reported separately. Do not infer any of these from a successful build:

1. Install on a clean real Android phone; confirm startup and branded icons.
2. Register/login with an existing account; close/reopen, token refresh, logout, account switching.
3. Real menu/cart/checkout, completed Paystack challenge, cancel/retry and verified return, member and guest.
4. Wallet, automatic funding, event/payment variants and native PDF/share actions.
5. GPS: precise/approximate, denied permission and saved address; map key acceptance.
6. Native OneSignal subscription, permission Allow/deny/re-enable, identified targeting; receipt and correct tap destination in foreground, background and swiped-away states. Android Settings → Force stop is a different OS state and normally prevents push until the app is reopened.
7. Keyboard/back/safe-area layouts and poor-network recovery across at least recent/older Android phones.
8. iPhone Safari Add to Home Screen, no Android APK CTA, and installed-web push on an eligible iPhone.
9. Permanent release signature, verified HTTPS App Links, APK download/install and a same-key version upgrade.

No real customer account, order, wallet movement or database cleanup is part of these build tests. The public release is intentionally activated through the main workflow; the acceptance limits above remain explicit.

## Public release and future updates

The requested public release uses GitHub-hosted APKs; Cloudinary upload access is not connected in this session. Main is the single source for website and Android UI. Frontend pushes on main build/sign Android automatically; backend-only changes need no APK. A successful verified main release is uploaded to GitHub Releases and updates `public/android-release.json`. That small pointer commit is pushed without force and deploys through the existing Vercel Git integration. The workflow excludes pointer-only changes to avoid a build loop and refuses publication from a stale main commit. No separate Android branch syncing is required after integration.

CI build codes use `10000 + workflow_run_number * 100 + run_attempt`; version names retain the source version with numeric build metadata. This keeps install/update codes increasing across releases and retries. Every release certificate is checked against the permanent App Links identity. Website visitors receive the current signed download; installed apps check on startup/resume, at most daily after a successful check, with a short retry delay after network failure. Manifest caching expires, so a long-running app can discover later versions. Installation remains an explicit Android action; no silent APK installation is attempted.

Native external referral/order/group links are canonical website URLs rather than WebView localhost. Legitimate staff deep links retain existing route/backend authorization. Native composed share images use a temporary content URI through Android's share chooser. All accounts and server role/campus permissions remain unchanged; this is not a claim that every staff/device-specific action has received physical-device acceptance.

Package inspection found an approximately 8 MB release, with most compressed space in Android/Capacitor/OneSignal/Firebase bytecode. Repository documents, SQL, backend files, private signing files and .git were absent from the APK. Browser notifications still belong to Chrome; recent OneSignal campaign payloads included the correct publicly reachable Holy Grills icon. The reported H needs screenshot/device interpretation, and no claim is made that Chrome's sender identity can be replaced by the native app identity.

Railway review: Celery already defaults to one child process, prefetches one task and lazily reuses a background-only Flask application. The repository API Procfile starts two workers/four threads. Actual Railway overrides and service RAM metrics have been requested before claiming measured savings or changing deployed process counts. Job frequencies were not reduced by the Android work.

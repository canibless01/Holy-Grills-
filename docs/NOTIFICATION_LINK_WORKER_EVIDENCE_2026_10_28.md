# Notification destinations and worker wiring — 28 October 2026

Filled missing destinations for literal application notification types: reward/campaign/ambassador grants, graduation, milestones, multiplier notices, streak cycle failures, kitchen gift work and operational stock/webhook alerts. Order references can supply the order destination when template data omits it. Missing order references still lead to the orders list. This is a registry and route contract check, not a claim that every notification has been received on a physical device.

Push links now resolve relative destinations against configured FRONTEND_URL before passing an absolute URL to the OS. Unsafe schemes, credential-bearing and malformed URLs are omitted. Each logical push dispatch gets one UUIDv4 idempotency key reused by its transport retries. This protects that retry loop; it is not a durable queue or cross-process replay recovery. OneSignal's official API documents the key and its 30-day deduplication window: https://github.com/OneSignal/onesignal-node-api/blob/main/DefaultApi.md .

Both notification UI surfaces use the same local/HTTPS navigation policy. Absolute same-origin URLs stay within the app; HTTPS campaign links open with noopener/noreferrer. A failed read receipt no longer blocks opening a notification. Controlled Chromium proves an unread cart notice opens /cart?reminder=1 even with a 503 read-receipt response. The safe-navigation script covers same-origin absolute, external HTTPS, query/hash retention and unsafe destinations.

The existing pending squad-HP recovery task was defined but absent from Beat. It is scheduled daily at 05:30 WAT and included in admin cron monitoring. Removed the obsolete duplicate send-scheduled-notifications job from expected cron status; the active blast dispatcher remains scheduled once. Registry tests load every Beat task and verify registration, unique targets, WAT timezone and the manual-only duplicate exclusion.

# Student loading and ambassador reward audit — 7 November 2026

## Student page loading

Dashboard now renders account/streak/tier/actions independently of order and lock panels. Recent orders have their own loading/error/retry state; an unavailable lock read does not fabricate a lock-in prompt. Wallet balances render independently of transaction history, while funding-return verification remains blocking and authoritative. Unknown wallet balances show a loading placeholder rather than an invented zero. Histories have retry feedback; completed funding no longer fetches the same history twice. HP-transfer eligibility reads run only when that feature is released.

Home and Menu use the same campus-scoped available catalogue query and existing 15-second cache. Home and Dashboard share a 15-second, account/campus/earned-total-scoped ranking query. Profile reuses the consistent campus/department/level snapshot. Financial balances, checkout totals, rewards and order status are not added to the catalogue cache. Server-rendered ranking queries do not retain a garbage-collection timer that prevents prerender exit.

## Ambassador rewards and community-manager controls

Meal discounts now validate ownership, active status, remaining uses and expiry directly during quoting. Read-only discount lists/quotes no longer run a global expiry UPDATE. Expired active records are represented as expired without writing customer records. Redemption locks only the selected benefit, and restoration preserves a voided status. Neither quote nor early cancellation can revive a voided benefit. The meal cap covers one eligible meal; customers can order above it and pay the difference plus delivery. Separate delivery benefits retain their existing rules.

The native SQL matrix reproduced cancellation reviving a voided discount before the fix, then passed after migration `20261107145806_ambassador_meal_discount_recovery`. It also verifies HP/free-side/meal grant receipts, duplicate protection, wallet debits, stacking, early restoration, partial/post-preparation refunds, expired/foreign/over-cap denials, and a ₦4,500 meal − ₦3,000 discount + ₦500 delivery = ₦2,000 successful wallet order. All fixtures rolled back.

Rewards now has a lightweight owned-meal-discount card, with value, uses, expiry, retry and a menu/checkout link. It does not require the ambassador tag still to be active to display an earned benefit. The existing reward-notification destination `/rewards` consequently exposes the benefit. Checkout has visible discount-loading failures/retry, clears unavailable selections on a successful refresh, and does not offer a meal discount for reward-only delivery.

Grant inputs reject fractional/out-of-range uses/validity, boolean money, noncanonical months and false-like override strings. Native required/min/max/step controls enforce the same terms. A voided grant replay cannot announce a newly issued reward. Reward notices have stable grant/channel identities, adopt legacy receipts and can recover a missing saved notice on an identical grant retry. Existing channel preferences remain respected. This does not add an automatic recovery scan for a process killed before the first notice attempt.

Promotional message and recipient rows now commit atomically using existing tables through service-only SECURITY INVOKER RPC `hg_create_ambassador_promo_atomic`; migration `20261107202218_atomic_ambassador_promo_distribution`. The modal retains its UUID across unchanged retries. The RPC checks actual active staff role, campus, eligible targets and immutable replay terms. Selected super-admin campus is respected; explicit global scope remains available to super admins. SQL rollback checks cover scope, active/inactive/student roles, unchanged/changed replay, interrupted distribution and helper grants. Global audience testing also rolls back its fixture message and assignments; nothing is externally sent.

Community-manager reads have visible retry states. Recommendations/decisions update rows in place, cancelling a prompt does not save, old-month responses are discarded, and switching month closes the grant modal. The approval action is labelled “Approve review”; issuing a reward remains a separate admin action. A first monthly review has safe default states. Request-local metric reads are reused only within the same request/actor/campus and invalidated after relevant mutations. Unchanged monthly metrics are not rewritten. Grant-history filtering happens before fetching another campus's grants. The atomic grant already saves milestone issuance, so no second post-commit marker write is required. Month-end fractional timestamps are included correctly.

Controlled mobile and desktop browser checks pass owned reward visibility/retry, choosing the discount, the ₦2,000 quote and submitted benefit ID, unchanged promo/grant retry payloads, native invalid-use prevention, manager recommendation/cancel and admin-only issuance. No real order/payment/notification broadcast was made. The mobile progressive-loading/catalogue/ranking/funding-return suite also passes. Unknown Dashboard balances/streaks use placeholders while their reads finish; funding verification stays blocking.
